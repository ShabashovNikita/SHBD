# Дизайн: движок меню на неделю

## Контекст

- Ответы анкеты лежат в DataStore (ключ `rationSurvey`, `RationSurveyAnswers` в
  `models/RationSurvey.kt`): приёмы пищи, бюджет + «Без ограничения», аллергены (11), «не люблю»
  (11), стоп-лист, время готовки (`NONE`/`QUICK`/`NORMAL`/`LOVE`), лимит повторов 1–3, дни готовки,
  техника (8), кухни мира (12, `ANY` первая), доставка (пока только запоминается).
- Цель калорий — `UserProfile.effectiveCalories` (её уже показывает итоговый экран анкеты).
- Доступ к активной модели ИИ — `FoodAnalysisService.callAi(...)` (приватный): он сам выбирает
  локальную модель на устройстве или облачного провайдера активного профиля, так работают
  «Пересчитать цели» и разбор еды. Готовность модели — `AppContainer.aiAvailability`
  (`READY` / `MODEL_MISSING`; `DISABLED` больше не встречается — ИИ всегда включён).
- Готового каталога в проекте нет. Есть проверенная продуктовая база и набор рецептов (JS) из
  открытого проекта меню на неделю с правилами подбора: фильтр по аллергенам/«не люблю»/стоп-листу
  /технике, лимит повторов, готовка партиями, подгонка порций, округление упаковок. Их переносим в
  JSON-каталог и Kotlin; лицензию учтём в изменении `licenses`.
- Пользователь решил: все рекомендации Рациона — через активную модель ИИ, без отдельной модели.

## Цели / Не цели

**Цели**
- Каталог продуктов и рецептов с кухней мира, минутами готовки, техникой и признаком «без готовки».
- Детерминированные и покрытые тестами правила: фильтр, проверка ответа модели, готовка впрок,
  порции, бюджет, список покупок.
- Выбор блюд — активной моделью ИИ; приложение гарантирует, что модель не нарушит анкету.
- Сохранение текущего плана и простой показ на итоговом экране, чтобы изменение можно было
  проверить в эмуляторе.

**Не цели**
- Экран недели, список покупок с зачёркиванием, рецепты по шагам, замены блюд, цветные точки —
  `ration-week-screen`. Анализ блюд и кеш — `dish-analysis-cache`. История — `ration-week-history`.
- Цены магазинов и доставка — после API (изменение 15). Цены в каталоге — средние, приблизительные.
- Перевод названий блюд и продуктов: каталог на русском, на английском интерфейсе названия
  остаются русскими (как у готовых блюд в каталоге). Перевод — позже, при необходимости.

## Решения

### 1. Каталог — JSON в `assets/ration/catalog.json`

Формат:

```json
{
  "version": 1,
  "products": [{ "id": "chicken_f", "name": "Куриная грудка", "aisle": "PROTEIN",
                 "priceRubPerKg": 349, "kcal": 137, "protein": 29.8, "fat": 1.8, "carbs": 0,
                 "allergens": [], "dislikes": [], "pantry": false, "unit": null, "unitGrams": null }],
  "recipes": [{ "id": "oml_classic", "name": "Омлет с сыром и овощами", "meal": "BREAKFAST",
                "cuisine": "HOME", "minutes": 15, "tools": ["STOVE"], "noCook": false,
                "items": [["egg", 130], ["milk", 40]] }]
}
```

- Значения `allergens`, `dislikes`, `tools`, `cuisine`, `meal`, `aisle` — имена перечислений из
  `models/RationSurvey.kt` (`Allergen`, `Dislike`, `KitchenTool`, `Cuisine`, `RationMeal`) и нового
  `ShopAisle` (`PROTEIN`, `DAIRY`, `VEG`, `FRUIT`, `GRAIN`, `OTHER`). Неизвестное имя — ошибка
  загрузки (ловится тестом целостности, а не у пользователя).
- `cuisine` по умолчанию `HOME`; `tools` пустой и `noCook = true` — блюдо без готовки.
- Почему JSON, а не Kotlin-список: каталог большой (~95 продуктов, ~140 рецептов), его удобно
  править и позже заменить загрузкой с сервера (`backend-accounts`), не трогая код.
- Перенос из исходной базы делается разовым node-скриптом (в scratchpad, в репозиторий не
  кладётся). Сопоставление:
  - аллергены: `nuts→NUTS, pnut→PEANUTS, glut→GLUTEN, lact→LACTOSE, eggs→EGGS, fish→FISH,
    sea→SEAFOOD, soy→SOY, ses→SESAME, citr→CITRUS, hony→HONEY`;
  - «не люблю»: `beef→RED_MEAT, pork→PORK, tofu→TOFU, eggp→EGGPLANT`, остальные (`MUSHROOMS`,
    `ONION`, `GARLIC`, `OLIVES`, `CILANTRO`, `SPICY`, `SUGAR`) проставляются по продукту вручную
    (грибы, лук, чеснок, оливки, кинза, острый перец/чили, сахар/мёд/сладкое);
  - техника: `stove→STOVE, oven→OVEN, blend→BLENDER, steam→STEAMER, grill→GRILL_PAN`, пустой
    список → `noCook = true`;
  - минуты: метка «без готовки» → 5, «быстро» → 15, `special` → 75, духовка → не меньше 40,
    иначе 30;
  - кухня: все перенесённые рецепты `HOME`, кроме явных (паста, ризотто → `ITALIAN`; плов →
    `CENTRAL_ASIAN`; хумус, фалафель → `MIDDLE_EASTERN` и т. п.), затем добавляются новые рецепты,
    чтобы у каждой кухни было ≥ 3 обедов/ужинов (около 35 рецептов, из продуктов каталога;
    новые продукты, если нужны, — с ценой и КБЖУ из открытых справочников).
- Мультиварка, аэрогриль и микроволновка в исходной базе не встречаются: рецепты требуют только
  перечисленную технику. Пока это значит, что эти отметки анкеты ничего не расширяют — допустимо;
  можно позже добавить рецепты под них.

`RationCatalogLoader.load(json: String): RationCatalog` — чистая функция (kotlinx.serialization);
`AppContainer.rationCatalog` читает asset лениво один раз.

### 2. Фильтр `RationDishFilter.allowed(catalog, answers): Map<RationMeal, List<Recipe>>`

Чистая функция, порядок проверок: приём пищи выбран → аллергены → «не люблю» → стоп-лист
(подстрока без регистра в названии рецепта и продуктов, `lowercase(Locale.ROOT)`, «ё»→«е») →
время (`NONE` → `noCook`; `QUICK` → ≤ 20; `NORMAL` → ≤ 60; `LOVE` → любое) → техника
(`tools ⊆ answers.kitchen`; пустой `kitchen` → только `noCook`) → кухни (если не `ANY`:
сначала выбранные кухни; если их меньше 7 для приёма пищи — плюс `HOME`).
Возвращает и короткие «причины пустоты» для приёма пищи без единого блюда (на экран: «Нет блюд
для ужина — ослабьте ограничения»).

### 3. Запрос к модели — `RationAiPlanner`

- В `FoodAnalysisService` добавляется `suspend fun completeText(prompt: String, op: String): String`
  = `callAi(prompt, imageBytes = null, op = op, reportPhases = false)`. Остальные функции не
  меняются. `RationAiPlanner` получает функцию `suspend (String) -> String` — в тестах фейк.
- Промпт (на английском для надёжности модели, ответ-комментарий — на языке интерфейса через
  существующий `ResponseLanguage`): цель калорий, выбранные приёмы пищи, бюджет на неделю или
  «unlimited», лимит повторов, дни готовки, и список кандидатов по приёмам пищи строками
  `id | name | cuisine | minutes | kcal | rub` (порция ×1). Кандидатов на приём пищи не больше
  25 (чтобы промпт влез в контекст локальной модели): если больше — берутся 25 по детерминированной
  перетасовке с seed = хэш ответов + номер недели. Модель просят: разнообразие, белок в каждом
  основном приёме, сумма ккал дня близко к цели, бюджет, повторы, по выходным при `LOVE` — блюда
  подольше.
- Ответ — только JSON:
  `{"days":[{"day":1,"BREAKFAST":"oml_classic","LUNCH":"...","DINNER":"..."}, ...7],
    "comment":"..."}`. Разбор терпимый: вырезается первый `{`…последний `}`, регистр ключей
  приёмов не важен, лишние ключи игнорируются, комментарий обрезается до 300 символов.
- Нет JSON или нет `days` → одна повторная попытка с припиской «Return ONLY JSON»; снова неудача
  → `RationPlanError.BadAnswer`. Ошибки сети/ключа/движка — как есть из `AiError` (текст ошибки
  тот же, что показывает Тренер).

### 4. Проверка ответа и заполнение слотов — `RationSlotRepair`

Вход: разрешённые блюда, сетка 7 × выбранные приёмы из ответа модели, лимит повторов. Для каждого
слота по порядку дней: id неизвестен / не разрешён / другой приём / превышает лимит → слот пуст.
Пустые слоты заполняются детерминированно (тот же seed): разрешённое блюдо этого приёма с
наименьшим числом использований, при равенстве — ближайшее по ккал к средней доле цели для
приёма. Если блюд не хватает даже с лимитом — лимит поднимается на 1 до заполнения, план
получает `repeatsRaised = true`. Число заменённых слотов сохраняется (`repairedSlots`) — для
отладки и чек-листа.

### 5. Готовка впрок

Только для `LUNCH` и `DINNER`, только если `cooks`. Дни плана — 7 дней, начиная с дня подбора
(день недели берётся из даты). Для дня готовки d блюдо слота готовится на `n = min(дней до
следующего дня готовки (включая d), repeatLimit)` порций; в следующие n−1 дней тот же приём
получает то же блюдо с `mode = REHEAT`. Эти слоты фиксируются **до** запроса к модели: модель
получает список «слот X = разогрев слота Y» и выбирает только слоты `COOK`; движок копирует
блюдо в слоты `REHEAT`. Повторы считаются по всем вхождениям (готовка + разогрев).
Пустые `cookDays` → все слоты `COOK`. Завтрак и перекус всегда `COOK`.

### 6. Порции и бюджет — `RationPlanBuilder`

1. КБЖУ и цена порции рецепта ×1 = сумма продуктов (граммы × значения на 100 г; цена ₽/кг ×
   граммы / 1000; продукты `pantry` в цену не входят).
2. Коэффициент порций — **свой для каждого дня**: `k = цель / ккал дня`, округление вниз до
   0,01, не больше 1,6 (нижней границы нет — день никогда не выше цели; погрешность округления
   порций — единицы ккал, предел +50 ккал). Перед этим дни, которым нужны порции вне 0,8…1,6,
   выравниваются заменами: жадно перебираются слоты `COOK` и разрешённые блюда того же приёма в
   пределах лимита повторов (разогревы меняются вместе с ними), берётся замена, сильнее всего
   уменьшающая суммарное отклонение дней от диапазона 0,8…1,6, до 40 замен. Цель — это
   `effectiveCalories` с дефицитом/профицитом. Цели нет → 2000 и `calorieGoalAssumed = true`.
   Модели в промпте сказано, что день не должен быть выше цели. Коэффициент дня хранится в
   `RationPlanDay.portionFactor`, `RationPlan.portionFactor` — среднее.
3. Стоимость недели считается **по списку покупок** (с округлением упаковок), т. к. это реальная
   сумма в магазине. Если бюджет ограничен и стоимость > бюджета: перебираются слоты `COOK` от
   самого дорогого блюда; блюдо меняется на самое дешёвое разрешённое того же приёма, которое не
   нарушит лимит повторов (разогревы меняются вместе с ним); после каждой замены — пересчёт.
   Стоп, когда уложились или замен нет. Итог: `weekCostRub`, `budgetRub?`, `overBudgetRub`.
   Порции ради бюджета **не** урезаются — это ломало бы цель калорий.

### 7. Список покупок — `RationShoppingList`

Сумма граммов по продукту за неделю: каждая съеденная порция (и разогрев тоже) × граммы × k
её дня. Округление упаковок: штучные
(`unit` = «шт», `unitGrams`) — до целых штук, яйца — до десятка; ≥ 1 кг — до 100 г; ≤ 120 г — до
10 г; иначе — до 50 г. Цена строки — от округлённых граммов. Группировка по `ShopAisle`;
`pantry`-продукты — отдельный список без цены.

### 8. Модель плана и хранение

`models/RationPlan.kt` (`@Serializable`): `RationPlan(createdAt: Long, startDate: String (ISO),
answersHash: Int, calorieGoal: Int, calorieGoalAssumed, portionFactor, days: List<RationPlanDay>,
shopping: List<ShoppingItem>, pantry: List<ShoppingItem>, weekCostRub, budgetRub: Int?,
overBudgetRub, repeatsRaised, repairedSlots, comment)`; `RationPlanDay(date, slots)`;
`RationPlanSlot(meal, recipeId, recipeName, mode: COOK|REHEAT, portions, kcal, protein, fat,
carbs, costRub)`. Название блюда копируется в план, чтобы старый план показывался, даже если
каталог обновится. Ключ DataStore `rationPlan` (`stringPreferencesKey`), функции
`rationPlan: Flow<RationPlan?>` / `setRationPlan(plan?)` в `PreferencesStoreRation.kt` тем же
`objectPref`. `answersHash` нужен будущему экрану, чтобы подсказать «ответы изменились —
подобрать заново»; в этом изменении не показывается.

### 9. Оркестратор и UI

`RationMenuService.build(answers, calorieGoal, today): Result<RationPlan>` = фильтр → слоты
впрок → `RationAiPlanner` → `RationSlotRepair` → `RationPlanBuilder` → сохранение. Перед вызовом
ViewModel проверяет `aiAvailability`: `MODEL_MISSING` → состояние `NeedModel` без запроса.

`RationPlanViewModel` (отдельно от анкеты, чтобы не раздувать `RationSurveyViewModel`):
`StateFlow<RationPlanUiState>` = `Idle(plan?)` | `Building` | `NeedModel` | `Failed(message)`.
На итоговом экране под сводкой (вместо текста `ration_survey_summary_coming`):
- нет плана → кнопка «Подобрать меню»;
- `Building` → индикатор + «Модель подбирает меню…» (на локальной модели может занять минуту);
- `NeedModel` → окно выбора модели, общее с Тренером (`AiModelSetupContent`): текст «Чтобы
  подобрать меню, нужна модель ИИ», «Установить локальную модель» (ход загрузки, отмена) и
  «Подключить удалённую модель» → инструкция (`CoachRemoteSetupDialog` с шагами для «Рациона»)
  → «Открыть ИИ-провайдер» (`ShbdRoutes.SETTINGS_AI`). Вкладка «Тренер» в тексте не упоминается.
  ViewModel подписан на `aiAvailability`: модель стала готова → `NeedModel` снимается и меню
  подбирается само; ИИ выключен → `Idle`. Ошибка `OnDeviceModelNotDownloaded` при подборе тоже
  даёт `NeedModel`;
- `Failed` → причина + «Повторить»;
- план есть → карточки дней («Пн, 3 нояб.»: приём — блюдо, «разогреть», ккал дня), строка
  «Неделя: 2 850 ₽ из 3 000 ₽» или «превышение на 400 ₽», пометки `repeatsRaised` /
  `calorieGoalAssumed`, комментарий модели, кнопка «Подобрать заново».
Подбор идёт в `viewModelScope` ViewModel вкладки «Рацион». Нижняя навигация сохраняет состояние
вкладки, поэтому при переходе на другую вкладку подбор продолжается и меню сохраняется, когда
модель ответит; отменяется он только при закрытии приложения (тогда план не сохраняется, на
экране снова кнопка).

### 10. Строки

`ration_plan_*` в `values/` и `values-ru/` (другие языки покажут английский, как у анкеты).
`ration_survey_summary_coming` удаляется.

## Риски / компромиссы

- **Локальная модель слабая и медленная** → кандидатов ≤ 25 на приём, короткие строки, жёсткий
  JSON-формат, починка слотов движком; даже плохой ответ даёт корректное меню. Минус: при плохом
  ответе меню фактически собирает движок — видно по `repairedSlots` (отмечаем в чек-листе).
- **Контекст модели** → оценка промпта: ~4 приёма × 25 строк × ~20 токенов ≈ 2 000 токенов +
  инструкции; должно влезать. Проверяется задачей ручной проверки на локальной модели.
- **Облачная модель отправляет ответы анкеты провайдеру** → как и Тренер; личных данных, кроме
  цели калорий и предпочтений в еде, не передаём.
- **Цены приблизительные и устаревают** → подпись «примерно» на стоимости; реальные цены — с API
  магазинов.
- **Каталог русскоязычный** → на английском интерфейсе названия блюд русские (записано в спеке).
- **Мало рецептов под редкие сочетания** (аллергии + «Не готовлю» + одна кухня) → понятная
  причина «нет блюд для …» вместо пустого меню.

## План миграции

Новые ключ DataStore и asset; старых данных нет. Откат — удалить ключ `rationPlan` (ответы анкеты
не затрагиваются).
